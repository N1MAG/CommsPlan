What Is HF Digital Tri-Mode?

HF Digital Tri-Mode combines three complementary families of amateur-radio software:

  • Fast Light: FLRig provides radio control, FLDigi supports digital-mode operation, and FLMsg and FLAmp support structured messages and file transfer.
  • JS8Call: provides weak-signal keyboard messaging, store-and-forward capabilities, and relay communication using JS8.
  • VarAC and VARA: provide chat, messaging, file transfer, BBS, and related services.

CommsPlan helps bring these independently useful applications together as a coordinated station. It can discover and configure application instances, maintain separate identities for multiple radios, manage paths and endpoints, monitor readiness, control application launching, associate schedules with radios, and collect supported traffic into a common station message library.

For multi-radio stations, CommsPlan keeps each radio's application profiles, ports, message locations, and launch identities distinct. Station-level services such as CommsPlan Spotter, FLAmp Q, CommStat, and the CommsPlan BBS can then work with received traffic according to the operator's configured access and publication policies.

This guide is a complete reference for the current CommsPlan interface. It documents each main-menu area, tab, button, table, and nested action so both new and advanced operators can move quickly and confidently.

Time model: schedule and SOP data are stored in UTC. Local/UTC toggles change display only.

Guide structure: new operators can read the sections in operational order, beginning with Configuration, followed by the schedule tabs and live operating tabs such as Ops Center, Inbox, and Map. During operation, the guide also serves as a workflow map: related tabs and configuration sections identify the source of shared behavior.

  • Control reference: each section identifies what the controls do and the operator decisions they support.
  • Operational context: major tabs, tab sections, and nested workflows identify the operational problem they address.
  • Feature relationships: CommsPlan is intentionally cross-connected. Schedules affect Ops Center and Map, operator rosters affect labeling and filtering, and Configuration shapes nearly every workflow in the application.
Tip: if a button appears muted, it usually means no eligible action is available yet. Select a row, start a net, or complete required fields to enable the next step.

Operating Plan Glossary

Purpose: these terms explain how CommsPlan connects planning, radios, scheduler behavior, messages, maps, and SOP output.

  • Frequency Plan: a reusable plan that describes where and when a radio should operate. It can include frequencies, schedule sources, operating groups, bands, modes, and operator notes.
  • Assigned Plan: the relationship between one radio profile and one frequency plan. A radio consumes an assigned plan; the plan itself remains reusable.
  • Operating Plan: the broader Where / When / What picture used during operations and SOP export. In this release, CommsPlan composes it from frequency plans, assigned radios, groups, procedures, message rules, and runtime context.
  • Schedule Source: the source of schedule or activity information, such as a public schedule, local group schedule, imported document, or manual entry.
  • Radio Profile: the execution or monitoring endpoint. It describes a radio, SDR, gateway, or observer setup, including software, control details, transmit capability, readiness, and assigned plan.

Plan Context Cue

Purpose: the plan context cue is a read-only line shown near the top of major planning and operating tabs so operators can confirm which radio and Frequency Plan the tab is currently describing.

Locations: HF Daily, HF Nets, Plan Builder, SOP Builder, Inbox, Ops Center, and Map.

  • Information shown: the selected or current radio profile, its assigned Frequency Plan, whether the radio is primary or active for the tab, and whether Scheduler, Messages, and Map participation are enabled for that radio.
  • Temporary hints: when applicable, the cue can show operator-visible state such as a current runtime override, blocked readiness, or disabled participation that explains why the tab may not be following the default plan.
  • Informational only: This cue is informational only. It does not change the active radio, send QSY commands, hold or resume the scheduler, filter Messages, filter Map, change SOP priority, or rewrite schedule rows.
  • Troubleshooting: check the selected radio in Configuration, Assigned Plans, runtime participation flags, and the schedule or SOP row that owns the intended operating change.

Quick Start

Goal: get one station configured in the same order CommsPlan expects to use it, so the scheduler, message workflows, map, and launch controls all agree with each other. Quick Start is intentionally more guided than brief. If a step feels unfamiliar, follow the link in that step before moving on.

  1. Start in Configuration and complete Operator Information: enter your callsign, name, state, and grid. This identity is reused throughout CommsPlan in filenames, message composition, operator matching, map context, and some automated defaults. If this section is wrong, later tabs can look confusing even when the software itself is working.
  2. Tell CommsPlan which software you actually use: in Configuration, choose the software stack that belongs to your station. This matters because setup review, status LEDs, launch behavior, and readiness guidance should reflect your real workflow, not every program CommsPlan is capable of supporting.
  3. Configure the core station behavior in CommsPlan Settings Details: this is where you decide how strongly the scheduler should enforce frequency changes, how prompts should behave, and what operating assumptions CommsPlan should make while you are active. Read this section if you are unsure why Ops Center seems advisory in one case and corrective in another.
  4. Configure software by task: open Configuration > Software, choose the software family, choose the radio that uses it, then choose the task. This keeps application work tied to the correct radio without turning the Radio page into a long software form.
  5. Configure HF Operating Groups before building group-based schedules: open Configuration > Main > HF Operating Groups and create each group the station uses, with at least one valid band, frequency, and mode configuration. Operating Groups supply the expected frequency, mode, VFO, FLDigi mode, and offset used by scheduling, Plan Builder, Ops Center, NCS, and QSY workflows. Group-based schedules need these definitions to resolve station behavior. A station that does not use group-dependent operation may leave groups empty.
  6. Build your operating plan: use the configured Operating Groups while building the actual schedule in HF Daily and HF Nets, then combine those schedule layers in Plan Builder. Configuration defines the station and its group behavior; the schedule tabs define when that behavior applies.
  7. Add optional helpers only after the core paths work: if you use station-specific scripts or support utilities, add them in Custom Tools Details. If you plan to launch supported software from CommsPlan, finish by reviewing Launch Control. This keeps the launch surface clean and prevents helper tools from being mistaken for primary integrations.
  8. Save, then read the setup review before moving on: save each edited radio or application in its owning editor, then open Station Setup > Review & enable. Review the saved setup and explicitly choose Enable scheduling when ready. Saving settings, starting CommsPlan, and opening a tab do not enable scheduling.
  9. Validate the plan in Plan Builder and Ops Center: Plan Builder helps you inspect the schedule you built; Ops Center shows what the live station thinks it should be doing now. If those two views disagree, the issue is usually in schedule design, group configuration, or software readiness rather than in Ops Center itself.
  10. Move into operating tabs only after the station definition is stable: use Messages for traffic review, compose, authentication, and BBS workflows; use Map for geographic context and SitRep visibility; and use SOP Builder for condition-driven action planning. These tabs become much easier to trust once the Configuration and schedule foundation is correct.
  11. If you are performing live net work, use the dedicated NCS tabs for that role: FLDigi / SSB, JS8Call, and VHF/UHF are not general setup tabs. They assume you already have a working station definition and now need role-specific operating support.
Recommended first-run mindset: finish the Configuration sequence first, then the schedule sequence, then the operating tabs. If you jump straight into Messages, Map, or an NCS tab before identity, software, and schedule are coherent, CommsPlan may still be functioning correctly but the experience will feel harder to interpret.

Ops Center

Purpose: primary operating dashboard for station state, schedule actions, and near-term decision support.

Operational use: Ops Center is the primary tab for monitoring live operation. It shows current activity, upcoming changes, schedule alignment, and software conditions that may make an immediate QSY unsafe.

  • Scope: short-horizon operating decisions, temporary holds, schedule confidence, and quick status review.
  • Out of scope: building schedules, maintaining rosters, or deep software configuration. Use the schedule tabs, Operators tabs, and Configuration for that work.
  • Cross-tab interaction: Ops Center reflects results from Configuration, assigned Frequency Plans, HF Daily, HF Nets, SOP Builder, Messages, and the software status providers. If the current plan or next action looks wrong, the cause is often upstream in one of those areas.

BBS Archive and Auto-Archive

Use this to keep your BBS folder clean without deleting files.

  • BBS concept: in VarAC, the BBS Directory is the live folder remote stations can browse and pull from. It is not the same as Incoming Files, which is where files addressed to you arrive, and it is not the same as Outbox, which is where files you want to send directly are staged.
  • Ordinary workflow: use +BBS or Compose's Add to BBS choice when you want a file offered through the VarAC BBS. Use Outbox when you want VarAC to send a file directly to a station instead of publishing it for later pickup.
  • Manage CommsPlan BBS: opens the top-level BBS service, which is authoritative for serving radios, locations, access, retention, publication, automation, preview, and visitor helpers. Native VarAC launcher, inbox, outbox, and radio paths remain in Configuration > Radios.
  • Managed BBS Library concept: CommsPlan keeps shared BBS content in a managed library, then publishes a clean copy into each selected radio's live VarAC BBS folder. Think of the library as the source of truth and each live BBS folder as the radio-specific on-air copy.
  • Virtual folders: menu names such as DOCDROP, INTEL, MISC, and ROOT are virtual aliases, not real nested folders inside the live BBS directory.
  • When to use Managed BBS Library: use the normal BBS workflow when one live BBS folder is enough. Use Managed BBS Library when you need controlled alternate file sets, menu-style browsing, callsign-aware visibility, per-radio published copies, or FLAMP relay block support.
  • Manual archive: click Archive on a BBS row to move just that file now.
  • Auto-archive timing: with Enable Auto-Archive on, checks run when you first open Messages after startup, then about once per day.
  • Age rule: files older than After <days> days are moved.
  • Required setup: BBS Directory and BBS Archive must both exist and be different folders.
  • Archived rows: archived BBS files stay visible in Messages with an [Archived] title prefix so you can still View or Delete them from the archive folder.
  • Operational inspiration: CommsPlan's VarAC BBS management direction is informed by KG5RKW's Vault and BBS Access Guard workflows.

Health Details

Purpose: Health Details shows what CommsPlan knows about the programs and scheduler checks that can affect station control.

Overview: CommsPlan depends on external programs and, in multi-rig operation, on the selected radio profile and its assigned current plan.   • Operator Lookup/Add: type a callsign, name, and state, or start typing a known operator. CommsPlan can complete known operators from the operator database. Then choose Add to TFC, Add to QRU, or Add to LATE. The add buttons place the station directly into the roster category you intend.

Live Actions, Copying, and Macro Files

This is the unusual part of the tab, and it is also the most powerful. The live action buttons do two related things: they copy text to your clipboard, and they keep macro-readable files current for operators who transmit with FLDigi macros. You can use either method. You do not have to use both.

  • Action For: choose the roster scope before clicking a live action. NCS means stations directed by NCS, including shared rows. ANCS means stations directed by ANCS, including shared rows. Shared means only rows directed by both roles. All means the full roster, ignoring Directed By.
  • ACK Needed: this copies the stations that still need an acknowledgement for the selected role. If Action For is NCS, CommsPlan finds stations directed by NCS that NCS has not ACKed yet, copies those station lines, and then marks them ACKed by NCS. ANCS works the same way for ANCS. If Shared or All is selected, CommsPlan copies a reference list but does not change ACK chips because no single role is acting.
  • Next TFC: this is for the traffic-handling part of the net. With NCS or ANCS selected, each click picks the next directed TFC station for that role and copies the callsign twice, for example W1ABC W1ABC. The repeated callsign matches common radio practice for clarity. The row changes from Pending to Now, and previously selected rows become Called. When no more traffic stations are available, CommsPlan clears the current next-traffic file so a macro does not replay an old callsign.
  • TFC / QRU / LATE: these copy the selected category using the current Action For scope. For example, with ANCS selected, QRU copies QRU stations directed by ANCS. With All selected, it copies the whole QRU category.
  • All Check-ins: this copies every station in the selected scope. Use Action For: All when you want the full roster, or NCS/ANCS when you only want the stations managed by that role.
  • Stations to Relay: this compare action is for the ANCS/NCS mismatch case. If your local roster has stations the partner list does not, CommsPlan shows the stations that should be relayed back to the partner.
  • Copy Relays: select one or more relay rows, then copy them for paste into TX. CommsPlan also writes the current relay selection to the role-specific relay file so macro-based operators have the same text available.
  • Action status: after a live action, CommsPlan shows a short message near the buttons and then clears it. Routine live-net actions do not interrupt you with an OK popup.
  • Save Check-ins: generated macro files update automatically as the roster changes. Save Check-ins is a manual checkpoint and final-log helper; it is not required before using ACK Needed, Next TFC, or the category files. CommsPlan highlights it when roster edits have not yet been saved.

Copied station-line format: copied lists use a station-line format such as N1MAG / Bill / CO / NCS 1RR. The role appears only for NCS/ANCS leadership rows, traffic appears at the end, and notes are omitted.

Macro-file integration: FLDigi macros can read text from files. CommsPlan keeps those files synchronized with the roster so a macro can transmit the current acknowledgement list, traffic list, or next traffic callsign without manual file editing during the net.

Copy scope and action: select Action For first, then select the action. The scope determines which rows are eligible; the action determines the copied text.

Plans: Local Nets

Purpose: keep a clear, local-time reminder calendar for nearby Amateur or GMRS nets and activities. A Local Net is an operator reminder, not an HF schedule row and not a radio-control instruction.

Resources: Frequencies

Purpose: manage reference data that can be selected from planning workspaces without making the catalog itself an active schedule, station configuration page, or radio-control surface.

Workspace model: Resources is one direct main-navigation destination. Inside it, use the browser-style tabs from left to right: Frequency Catalog for channels and frequencies, Net Directory for net identity and published net meetings, and Import / Export for preview-first exchange. Search results are bounded so normal catalog work remains responsive.

Frequency Catalog

  • Reference versus station resource: bundled and imported records retain their catalog source internally, while normal screens show its readable name instead of database keys or version hashes. A station-owned record is the right choice for a locally maintained simplex frequency or repeater pair.
  • Frequency display: frequencies use decimal MHz, such as 7.115 MHz. CommsPlan retains exact integer-Hz values internally for comparison and scheduling.
  • Reference guidance: catalog wording such as Within selected reference is advisory. CommsPlan does not determine a license class, location, equipment certification, emission authorization, or whether you may transmit.
  • Used by: inspect this before changing a resource. It shows the saved Local Nets, directory sessions, or other consumers that retain a reference to it.
  • Retire instead of delete: retirement removes a record from normal selection while preserving its identity and history. A referenced record cannot be silently removed. Hard deletion is only available after CommsPlan proves there are no references and asks for confirmation.

Net Directory and HF subscription

  • Directory identity is not a schedule. A directory entry describes a net; published net meetings describe its reusable timing and frequency context. Listed means an item is available in the catalog—it does not mean the net is happening now or that your station follows it. Neither a listing nor a meeting activates an HF or Local schedule on its own.
  • Source region: this describes where a listing originates or is primarily organized. It does not restrict who may listen.
  • Add to HF Nets: select one or more published net meetings, choose Add to HF Nets, then review the proposed rows in the named HF Net schedule before saving. This is an explicit subscription workflow, not an automatic import into a live schedule.
  • Add to Local Nets: choose a published net meeting in the Local Net editor to prefill a reminder draft, then review group, frequency, recurrence, and timezone before saving.
  • Updates do not rewrite schedules. A changed directory resource can mark a linked Local Net as needing review, while the accepted reminder snapshot remains unchanged. Review the directory and saved reminder deliberately before making any edit.

Import, export, and recovery

  • Preview first. Import reads a chosen JSON file and shows diagnostics before Apply Preview becomes available. Cancel Preview leaves the catalog unchanged.
  • Source protection. Imports do not overwrite bundled read-only records. Resolve invalid, duplicate, ambiguous, or conflicting preview items before applying an exchange.
  • Export is selective. Enter the stable frequency or net keys you want to exchange; export does not imply publication, scheduling, or radio action.
  • Recovery mindset. Keep an export before a large catalog change. If a change must be reversed, restore or re-import a reviewed exchange rather than editing an active schedule or deleting a referenced source record.

Operating Groups in resource workflows

Operating Groups describe the group context of an activity; they do not prove membership, authority, licensing, or a radio assignment. In Local Nets, choose a configured group to make the reminder easier to filter and recognize in Ops Center. Frequency Catalog and Net Directory records may carry group context as reference information. Keep a local activity unassigned when no configured group applies.

The result uses these classifications exactly:

  • Imported: new operator rows accepted by validation.
  • Updated: existing operator rows matched and refreshed by the import.
  • Blank ignored: blank or separator rows with no operator record.
  • Section/legend ignored: recognizable headings, notes, or legend rows such as New additions or * = Signal only.
  • Invalid skipped: an intended operator row that fails validation. A blank or recognizable section/legend row is ignored, not a skipped valid operator.

Warnings identify the CSV line, callsign text, field, and reason. Use the preview's copy/export diagnostics action before committing when you need a support record or want to correct the source file. Export the roster after a successful import if you need a separate operator-data checkpoint.

Supplied MAGNET roster: the expected parser result is 166 imported, 18 blank ignored, 4 section/legend ignored, and 0 invalid skipped; child groups MR01 through MR10 are detected.   3. 3) Fill in the profile header: confirm the name and decide whether you want the profile to be saved as active right away.
  4. 4) Build the procedure: use Add action, complete What, When, and Details, then choose Use action. Repeat and review the accumulating summary before opening conflict review.
  5. 5) Review action state: inspect the summary for disabled, unresolved, or pending actions. Local Comms actions do not participate in HF conflict checks.
  6. 6) Expand the Conflict Workbench only after the rows are mostly complete: this keeps the builder stable while you make multiple edits and reduces context switching.
  7. 7) For timing conflicts, use Suggest first: if a timing shift is possible, the suggested start will be precomputed for you. If the conflict is not time-based, the field stays neutral so it does not imply a missing required value.
  8. 8) Apply per-conflict priority only when needed: use the workbench buttons to choose SOP, Net, or Daily priority for the selected conflict row, or use the builder defaults when that matches your plan.
  9. 9) Save the SOP: Save re-runs the validations, applies required policy decisions, and updates the active-state logic.
  10. 10) Switch to HF Daily immediately after saving an active HF SOP: this is where you confirm the actual runtime sequence, run Resolve Conflicts if HF overlap still exists, and verify the final effective timeline.
  11. Rule: same-frequency SOP overlaps are allowed and are not shown as conflicts because they do not require a frequency change.

JS8Call Settings Details

Where to configure it: open Configuration > Software, choose JS8Call, then choose the radio and task. CommStat, External Spotter, and CommsPlan Spotter are intentionally not JS8Call settings.

  • Host and Port: tell CommsPlan how to talk to JS8Call on this computer. Most local stations use host 127.0.0.1 and port 2442.
  • Offset (Hz): the JS8 audio offset CommsPlan should expect when checking schedule alignment. If js8_offset_hz is 0, it remains interpreted as “offset enforcement not configured.” Otherwise CommsPlan sets and verifies it. If you are unsure, start with your normal JS8 operating offset and adjust only when your group uses a specific offset plan.
  • Mark JS8Call MSG Read?: controls whether CommsPlan should also mark JS8Call inbox messages read when you mark them retrieved in CommsPlan. Leave it off if you want JS8Call to keep its own unread state untouched.
  • Load JS8 Traffic: manually rebuilds JS8 traffic evidence used by Messages, Map, and related views. Use it when you changed paths, imported data, or want CommsPlan to reread current JS8 traffic without waiting for the next normal refresh.
  • JS8Call Application: select the JS8Call application or executable used by this radio. CommsPlan recognizes stock JS8Call, JS8Call-Improved, and Subspace package names. Linux installations may use a system executable such as /usr/bin/js8call-subspace or the Improved user install at ~/.local/bin/JS8Call.
  • Modern JS8Call variants: CommsPlan uses each radio's configured TCP endpoint and a stable, distinct --rig-name for independently launched JS8Call 2.2.0, Improved 3.0.3, and Subspace instances. Each instance must use unique API ports and a distinct message-storage namespace. CommsPlan treats Subspace as rig-scoped under the current compatibility assumption, but still labels storage Needs verification until live file evidence confirms the resolved data root.
  • Save folder: this is JS8Call's SaveDir for operator-saved or received transfer files. It is separate from Message storage, which owns ALL.TXT, DIRECTED.TXT, and inbox.db3; changing the save folder does not relocate message logs or the inbox database.
  • Read JS8Call messages from: this shows the effective native message files CommsPlan will read, including the profile's normal paths and any explicit per-file overrides. Changing a launch executable or named profile does not silently relocate these sources; keep the previous files when they are still the intended station history.
  • Message storage status: each radio shows Isolated · <rig name>, Shared, or Needs verification. Review the affected radio configurations before running concurrent local instances when storage is shared or needs verification.
  • JS8Call DIRECTED.TXT: the JS8Call file that records directed traffic. CommsPlan reads it so operator activity and link evidence can appear in CommsPlan views.
  • CommStat: configure the optional CommStat launcher under the separate CommStat family. It maps to the selected radio's JS8 transport and can provide structured STATREP-style station awareness. Learn more at commstat.app.
  • Spotter: configure optional External Spotter executable/database/source paths and explicit imports in External Spotter. Manage the active station CP Forms Library, mappings, rules, Expect queries, watches, forms, and activity from top-level CommsPlan Spotter. External Spotter activity and imports remain awareness data; they do not enable live CommsPlan rules.
  • Auto-Classify: asks CommsPlan to make a first guess about each form. For example, common check-in forms are marked for Net Control, SitRep forms are marked for status/map use, and alert-type forms are marked for alert handling. Treat this as a starting point. Your group may use a form differently, and you can change the purpose or checkboxes before saving.
  • Purpose: describes what a JS8Spotter form means to your operation. This is the plain-language label CommsPlan uses to decide whether a form is a net check-in, a situation report, a weather report, a net notice, an information request, or something else. If a form should be ignored by CommsPlan, choose Ignore.
  • Messages: shows matching received JS8Spotter forms in the Messages tab. Turn this off for JS8Spotter forms you want CommsPlan to keep out of the operator message list.
  • Map: lets a received JS8Spotter form count as map evidence when CommsPlan already knows where the sending station is. This does not guess a location from random form text. It allows known-station reports to appear in map layers such as Weather, Alerts, Infrastructure, and Medical.
  • Alert: makes unread matching JS8Spotter forms stand out as alerts in Messages and lets alert-style forms feed the alert layer when map routing is also enabled. After the message is marked read, it behaves like a normal read message.
  • Net: lets Net Control workflows use that JS8Spotter form. This is how a group-specific check-in form can feed JS8 NCS without CommsPlan hard-coding every possible form number.
  • Status: lets a JS8Spotter form feed the shared status view when CommsPlan knows how to read that form's status fields. Today this is intentionally conservative: F!104, F!301, and F!304 can become normalized status. Other JS8Spotter forms can still be routed to Messages, Map, Alerts, or Net Control, but deeper status field reading requires explicit support.
  • Map category behavior: new JS8Spotter forms can often be routed by changing the mapper purpose and checkboxes, without a code change. A code change is only needed when CommsPlan must understand new form-specific fields deeply enough to create a specialized summary, severity, or status value.
  • Default behavior: if you have not saved a custom mapper, CommsPlan keeps the legacy behavior for the standard known forms. Once you save mapper rows, the checkboxes become the source of truth for how those forms flow through CommsPlan.
  • Auto-Fill status: after an auto-fill attempt, CommsPlan reports what it found or what still needs attention. Treat this as setup guidance, not an error unless a feature you need remains missing.

The Repair FLMsg / FLAmp components… action remains available on the FLMsg, FLAmp, Message Folders, or Launch task for review and recovery after later system changes. Operating Groups Details

  • Purpose: Operating Groups are the reusable link between a named activity and its expected station behavior. HF schedules use their frequency, mode, VFO, FLDigi mode, and offset; Plan Builder, Ops Center, NCS, and QSY workflows use the same definitions when resolving what the station should do.
  • Configuration location: open Configuration > Main > HF Operating Groups. The section is part of the station-wide configuration rather than a single radio's Software Administration record.
  • Group-based scheduling: configure Operating Groups before creating schedules or actions that refer to group behavior. The group supplies the concrete frequency, mode, and related expectations. No groups is valid for operation that does not depend on group plans; only workflows that require a missing group need correction.
  • Minimum useful configuration: enter a recognizable Group name and select Mode, Band, Frequency, and VFO. For digital operation, also set the expected FLDigi Starting Mode and FLDigi Offset. Use Save Changes to validate and immediately persist the configuration.
  • Groups and configurations: one named group can contain several frequencies in the same band and mode, as well as configurations for different bands or modes. Select the group first, then select a configuration row to review its VFO, FLDigi, auto-tune, condition-level, and Fast Light naming details. Add Configuration adds another frequency configuration without creating a different group identity. Select the exact frequency in schedules, SOP actions, and QSY choices. If a referenced frequency is edited, deleted, or ambiguous, review and select it again; CommsPlan does not silently substitute another configuration.
  • Known groups: Known Groups from Net Resources lists recognized groups supplied by the net-resource catalog. View Frequencies previews the available configurations; Enable Group copies supported configurations into the station's saved Operating Groups for review. Planned or unsupported entries are not silently enabled.
  • Mode choices: choose Digi for digital-mode work such as JS8 or FLDigi workflows, and SSB for voice net work.
  • Voice sideband behavior: when Mode=SSB, FLDigi Starting Mode defaults to band-appropriate sideband (LSB on lower HF bands, USB on upper HF bands), and can be manually overridden.
  • Key table columns: Selected, Group, Mode, Band, Freq (MHz.kHz.Hz), VFO, FLDigi Starting Mode, FLDigi Offset, Auto-Tune, and Use Condition Levels.
  • Frequency: enter the operating frequency as decimal MHz, such as 7.078, or in the readable MHz.kHz.Hz form shown by the editor, such as 7.078.000. CommsPlan validates the value against the selected band and mode and uses it when comparing the active station with the schedule.
  • VFO: choose the radio VFO the plan expects, usually A unless your station has a reason to use another VFO.
  • FLDigi Offset meaning: this is the expected FLDigi audio offset for the group row, such as 900. If a schedule row omits FLDigi offset, the matching Operating Group value is used as the expected offset.
  • Auto-Tune on QSY: allows CommsPlan to tune this group configuration automatically when schedule enforcement calls for it and the radio's control and safety policies also permit the action. Leave it off when operator confirmation is required.
  • Drift behavior: FLDigi offset may move during operation and appear off plan. Whether CommsPlan corrects it immediately or asks first depends on the FLDigi enforcement mode; active net operation can also suppress scheduler corrections.
  • Condition levels: condition-level participation is group-scoped. Changing Use Condition Levels on one configuration applies to every configuration with the same Group name, allowing SOP condition layers to select the appropriate group behavior without redefining the schedule.
  • Fast Light naming: the selected group can define filename delimiter, signed and unsigned suffix, and preferred form-family behavior used by Fast Light message workflows. These naming choices are group-scoped and do not change the scheduler frequency.
  • Change impact: after changing or deleting a group configuration, review HF Daily, HF Nets, Plan Builder, and RF Guard for schedules that reference that group. CommsPlan does not treat an Operating Group as a radio assignment or transmit authorization.
  • Local reminder context: selecting a group in Local Nets improves filtering and Ops Center recognition. It does not assign a radio, authorize a transmission, enable a scheduler action, or activate an SOP.
  • Condition-level concept: condition levels let you pre-stage several operational postures without rewriting the whole schedule every time conditions change. Instead of editing frequency plans during an event, you can move the station's active level and let CommsPlan reveal only the rows meant for that level.

Local Comms Groups Details

  • Group: the team or local operating group name.
  • Resource: the practical resource name, such as a repeater, simplex channel, tactical channel, or local net.

Local Mesh

Purpose: connect CommsPlan to station-level MeshCore or Meshtastic services so received text and position evidence can join the canonical Inbox and Map without pretending that a mesh device is an HF radio profile.

  • Saved Devices: choose a named saved connection, then Connect or Disconnect. Add device… starts a new identity instead of overwriting another saved device. The visible connection name is separate from the advertised Bluetooth name. The compact context shows one connection state so saved configuration and runtime connectivity are not confused.
  • Add or find a device: choose Add device… to open discovery or manual connection choices. Find nearby device… opens bounded discovery for the selected connection without changing its saved identity. For MeshCore, select the exact discovered device before saving. Keep CommsPlan open. Connect uses an existing operating-system bond when available; on Linux, if secured service discovery indicates that the device is not paired, CommsPlan makes one bounded pair-before-connect attempt and the desktop asks for the PIN displayed by the device. CommsPlan never stores the PIN. If Linux reports that Bluetooth is powered off, cancels the connection, or cannot complete pairing, CommsPlan pauses automatic reconnects; restore Bluetooth/card availability, wait for advertising, then choose Connect once.
  • Protocol: select MeshCore or Meshtastic. CommsPlan exposes only transports supported for that protocol and retains a stable adapter/connection identity for reconnect and audit.
  • Connection: configure the applicable TCP host/port, USB serial device and baud, saved BLE device identity, or HTTP base URL. Prefer the stable BLE identifier captured by discovery; the advertised name is a fallback and operator clue.
  • MQTT bridge: retained legacy broker and topic-root settings are not an active local transport in this release.
  • Use Data For: Inbox stores received mesh text in CommsPlan's message pipeline. Map allows available node positions to contribute map context. Source labels preserve which mesh connection supplied the evidence.
  • Allow Send: shown directly in Saved Devices so outbound permission is visible without opening Advanced connection details. It is available for qualified Meshtastic and MeshCore TCP/USB/BLE connections and is off by default. MeshCore Bluetooth sending uses the official MeshCore client over the same connected session as receive. Enabling ingest, Inbox, Map, or a channel policy does not authorize outbound traffic.
  • Outbound workflow: after enabling Allow Send, connect the device and use Messages > Compose > Local Mesh. Only accepted channel policies and known direct nodes are selectable. CommsPlan requires a final confirmation and prevents overlapping sends through the same adapter.
  • Channel policy: Add public channel… stages a public policy for review, and Add Private Feed stages a private policy; configure its encryption key on the device before accepting it. Use channel in CommsPlan and Ignore in CommsPlan change CP policy only. Configure device… and Remove from device are explicit device actions, while Remove from CommsPlan archives the CP policy without changing the device.
  • Check connection: rechecks the selected saved connection and reports actionable missing fields or a retry reason. It does not silently connect, send, or reconfigure the device.

VarAC Settings Details

Where to configure it: open Configuration > Software, choose VarAC, then choose the radio and task. Use top-level BBS for station catalog, locations, access, retention, publication, automation, initialization, visitor preview, and visitor helpers.

Concept of use: treat the VarAC paths as three different jobs. Incoming Files is where files addressed to you arrive. VarAC Outbox Directory is where CommsPlan stages files that VarAC should transmit directly. BBS Directory is the live published file shelf remote stations can browse and pull from.

  • VarAC identity: the direct editor keeps the CommsPlan radio name, native rig name, instance label, launcher choice, and INI/Wine paths as separate fields. Existing cluster membership remains visible when supplied by the saved profile; the editor does not invent a cluster or overwrite a manual path.
  • Resume an interrupted cluster add: if a prior attempt saved the intended cluster and its first radio but not the new radio, CommsPlan labels the exact match Resume … — Recommended and shows the next member number. Select that explicit choice to finish the existing cluster; do not create a second cluster with the same radios.
  • Manual paths and optional discovery: browse or type the existing VarAC application, INI, database, VARA runtime, incoming, outbox, BBS/archive, and working-directory paths. Find may suggest a cached path, but applying it is explicit. No native VarAC/VARA preparation runs automatically.
  • Linux/Wine VARA paths: when VarAC is installed inside a Wine drive, CommsPlan creates each radio's distinct VARA runtime inside that same drive, using a readable name such as C:\VARA-ft-710\VARA.exe. CommsPlan does not give VarAC a Z:\...\.freqinout executable path. It never replaces an existing runtime; an occupied preferred folder is preserved and CommsPlan selects the first unused numbered sibling.
  • Older managed Linux/Wine setups: after restart, CommsPlan can automatically repair an exact older CommsPlan-managed VARA runtime that was saved below .freqinout. The bounded repair runs only when VarAC and VARA are stopped, copies the runtime to a new unused folder inside the verified Wine drive, backs up and verifies the changed INI, and synchronizes Software Administration and Launch Control. The old folder is retained. Ambiguous, unsupported, missing, or running setups are left unchanged and logged for review.
  • Legacy launch and Windows: older Linux/Wine launch commands are converted to an exact executable-and-INI argument vector so the Windows path backslashes are preserved. On Windows, CommsPlan uses the native VarAC.exe, native member INI, and native working directory; it does not add Wine, a Wine prefix, or a Z: path.
  • Station Setup and Software Administration: both screens describe the same saved VarAC identity. The application, INI, database, VARA runtime, incoming, outbox, BBS/archive, working directory, and launch details saved in the direct editor reappear for that radio in Software Administration.
  • What a cluster shares: members normally use the same VarAC program/install working directory, one cluster database, and one cluster BBS/archive. Each radio still has its own VarAC INI, copied VARA runtime and VARA INI, incoming folder, outbox, ports, and cluster member number. Reusing the common install folder is expected and is not a conflict; reusing a member-specific path or number is blocked to protect the existing radio.
  • Saved cluster visibility: after Station Setup saves a cluster, that saved cluster and its members automatically appear in VarAC Cluster settings. A stale hidden/setup preference cannot conceal saved topology; remove the saved cluster before turning cluster setup off.
  • Recommended setup order: start with VarAC Install Folder, Incoming Files, and the normal BBS folders. Confirm basic send/receive and BBS behavior before enabling Managed BBS Library or BBS Access Guard.
  • Paths & Launch: tab for the selected radio's VarAC application path, launch command, INI path, incoming-file folder, outbox folder, and multi-instance cluster setup.
  • Radio Paths: tab for the selected radio's VarAC install, launch, INI, incoming, outgoing, and cluster setup.
  • Radio Live BBS: tab for the selected radio's live BBS folder, BBS archive folder, BBS access settings, and allowed callsigns.
  • Shared Library: tab for shared CommsPlan-managed locations, library policy, access-code state, FLAMP relay, and the content that can be published into each radio's live BBS folder.
  • Access Guard: separate tab for inbound file protection. BBS Access Guard is not the same service as the Managed BBS Library.
  • VarAC Install Folder: the VarAC program location. CommsPlan uses this for launch/orchestration and to help infer other VarAC resources.
  • VarAC Launch Command (Advanced): advanced override. Leave this blank unless VarAC needs a special start command on your station, most often on Linux/Wine.
  • VarAC Incoming Files: VarAC's receive folder for files delivered to you. This is not your BBS folder.
  • VarAC Outbox Directory: where CommsPlan stages files that VarAC should send directly. Use this for operator-to-operator delivery, not public BBS publication.
  • VarAC INI File: optional direct path to VarAC.ini. Use this when auto-detection is not enough or when you want to sync BBS policy from the authoritative INI.
  • BBS Directory: the live published VarAC BBS folder. Remote stations see the files in this directory when they browse your BBS.
  • BBS Archive: where archived BBS files are moved. This keeps the live BBS tidy without deleting older files.
  • Auto-Archive Policy: group containing Enable Auto-Archive, After, and days. It moves files older than the selected age from BBS Directory to BBS Archive.
  • Enable BBS: turns VarAC BBS service on or off in CommsPlan's BBS policy view.
  • Limit Access To Callsigns: restricts BBS access to a defined allow-list. This is strongly recommended if you want a controlled BBS.
  • Allowed Callsigns: the allow-list used when access limiting is enabled. CommsPlan supports lookup-assisted management to reduce typos. In single-rig, this list applies to the station's VarAC BBS policy.
  • Announce: mirrors VarAC's BBS announcement behavior so users can choose whether the BBS is advertised.
  • Native BBS import: use BBS > Radio Service > Get from VarAC… to review and import the selected radio's supported native BBS values.
  • Native BBS update: use BBS > Radio Service > Update VarAC… after saving CommsPlan policy. Review targets and close VarAC before writing; CommsPlan backs up and verifies the supported native BBS settings.
  • Managed BBS Library: the shared library and FLAMP relay workflow. It publishes selected library views into a radio-specific live VarAC BBS directory while keeping each VarAC instance's live folder stable.
  • Library vs live BBS: think of the shared library as the storage room and menu system. Each live BBS Directory is the on-air shelf for one radio. VarAC only needs to know about its radio's live shelf; CommsPlan decides what library content is copied there.
  • BBS file management: the Messages BBS view shows VarAC incoming files, outgoing files, live BBS files, managed library locations, and archived BBS files with a source-area label so the operator can tell where each file lives before archiving or deleting it.
  • CommsPlan BBS: the top-level station service for choosing serving radios, defining locations and access, publishing files, checking the visitor view, and reviewing visitor helpers.
  • Enable Managed BBS Library: turns on the service that watches VarAC session traffic and publishes managed views into live BBS folders. This is the operational on/off switch for the library workflow; it does not erase your library folders.
  • Turn on CommsPlan-managed BBS menus.: the short UI explanation shown beside Enable Managed BBS Library.
  • Set up BBS files…: available from top-level BBS > Radio Service. Choose the existing live folder, choose whether to reuse its current files or start an empty Default location, and review the final action before the worker writes files and enables the selected radio's BBS service and catalog publication. Repeating setup reuses the existing catalog without replacing the live folder or duplicating same-named imported files.
  • Create the FIO_BBS_Vault folders next to the live VarAC BBS folder.: the short UI explanation shown beside Set up BBS files….
  • Return Live BBS Home: republishes the default location into the live BBS folder. Use this operational recovery action when you want callers returned to the main menu immediately, for example after testing a controlled location. It does not reset configuration, locations, access, retention, or catalog membership.
  • Managed Root: automatic CommsPlan-managed storage for named locations, audit state, and publish manifests. In the current release it is always created next to the live BBS Directory as FIO_BBS_Vault; it is not a free-form operator override.
  • Managed Root structure: the normal layout is Managed Root/locations/<Location Name> for operator-maintained source folders, plus Managed Root/runtime/manifests, runtime/logs, and runtime/tmp for CommsPlan bookkeeping.
  • Managed Root example: if your live BBS is /Users/you/Radio/VarAC_files/BBS, the library root will be /Users/you/Radio/VarAC_files/FIO_BBS_Vault, and a location named TEST_A will normally use FIO_BBS_Vault/locations/TEST_A.

  • Library Session: section for default-menu identity, timers, bad-code behavior, request parsing, and FLAMP relay options.
  • Default Location: read-only display for the CommsPlan-managed root BBS menu. This is not the same thing as the VarAC BBS Directory. The VarAC folder is the live shelf callers browse; Default is the managed source view that CommsPlan publishes there when the BBS is at the main menu. The adjacent Info button explains this distinction in the UI.
  • Default view rationale: the default view provides a predictable starting point. It normally contains helper files such as BBS MSG - Type INTEL to open Intel then refresh BBS.txt, rather than every file from every location. This keeps the initial BBS listing readable and allows callers to choose the required location.
  • Global Code Policy: the station-wide default for how cautious alternate locations should be. The normal friendly default is to allow public locations, then set access rules per location. Use stricter global policy only when your operating plan says non-default locations should normally require codes.
  • Request Parsing: controls how CommsPlan recognizes caller commands in VarAC traffic. The normal mode is command-prefix style: a caller refreshes the BBS, types an alias such as INTEL, then refreshes again. Compatibility parsing also accepts more explicit forms such as BBS OPEN INTEL. Exact-code-oriented workflows are available for stations that want the code itself to be the access command, but alias-plus-code is usually easier to explain on-air.
  • Return Mode: decides when the BBS goes back to the Default menu. On disconnect is the cleanest normal choice because each caller gets a fresh menu. After inactivity timeout is useful when disconnect lines are unreliable. Manual operator reset only is for deliberate operator-controlled sessions where a special location should remain published until you reset it.
  • Return Timer: used with inactivity-based return behavior. Choose a value long enough that a slow operator has time to read, request, and refresh without being pushed back to the main menu mid-session.
  • Bad Code Limit: how many bad codes are tolerated before cooldown is applied. This is a guardrail against repeated mistakes or guessing, not a cryptographic security system.
  • Cooldown: how long CommsPlan waits before accepting another bad-code attempt from that sender after the failure threshold is reached. It keeps a caller from hammering the same protected location while still allowing them to try again later.
  • FLAMP Relay: row that contains Enable FLAMP relay service, the relay folder field, and a Browse button.

BLKS 0,1 F277, BLK 0,1 F277, BLOCK 0,1 F277, and BLOCKS 0,1 F277 request a temporary BBS file containing those blocks.

  • FLAMP relay folder: placeholder text in the relay folder field. This is the source folder where CommsPlan looks for relay queue files to advertise and serve as temporary synthetic BBS responses.
  • Limit FLAMP listing to files newer than: limits queue listings to recent relay files, with choices such as 3 days, 5 days, 7 days, 10 days, 14 days, and 30 days.
  • FLAMP relay auto-fill: if your FLAMP/rx path is set, CommsPlan will usually suggest a sibling relay folder automatically. This is a convenience default; you can override it whenever your station uses a different relay path.
  • CommsPlan Managed Locations: section for named virtual folders that can be published into the live BBS. The table columns are Name, Alias, Filesystem Location, Enabled, Visible, and Code Active.

  • Save Location: stores the current location definition in CommsPlan so it can be published later.
  • Delete Location: deletes the selected non-default location definition from CommsPlan. The Default location cannot be deleted.

  • Alias: the short command a remote station types, such as INTEL or DOCDROP.
  • Custom Helper Text: optional operator-written text appended to the generated helper filename. CommsPlan writes the command instruction automatically; your custom text should tell the caller what the location holds. For example, the generated portion might say Type AIB to open AIB then refresh BBS, and your custom text might add weekly AIB reports.
  • Helper Filename: live preview of the helper file name CommsPlan will publish for this location in the root BBS menu.
  • Location Folder: the managed folder whose files will be published when that location is active. The safest normal pattern is a dedicated folder under Managed Root/locations in the VarAC BBS area. This is where you place files from your computer when you want that location to publish them. In the current release, nested subfolders are ignored.
  • Location Folder defaults: when you create a new location, CommsPlan suggests Managed Root/locations/<Location Name>, shows likely live-BBS name matches, and can create the missing folder on save so you do not have to hand-build the layout first.
  • Enabled: table checkbox/column for whether that location can be published.
  • Visible in Root Menu: controls whether the alias is advertised in the root menu. Hidden locations can still exist for controlled direct-access workflows.
  • Visible: table column that mirrors whether the location is visible in the root menu.
  • Access Policy: controls whether the location is public, callsign-limited, requires an access code, or requires both an allowed callsign and a code.
  • Inherit Global Allowed Callsigns: applies the normal BBS allow-list to that location. This is the safest default.
  • Location Allowed Callsigns: optional stricter subset for that location. Use this when a special location should be opened only by certain stations even if the main BBS allow-list is broader.
  • Access Code / Confirm Code: operational code used to open a non-default location. CommsPlan stores the code locally for the station operator to view later and also keeps a hash for caller verification. This is workflow control for off-grid operations, not strong secrecy; if a code changes, you still need an operational way to share the new code with the right stations.
  • Root menu helper files: when the library is publishing the default location, CommsPlan injects synthetic BBS helper entries into the live BBS such as BBS MSG - Type TEST_A ... then refresh BBS. These are instructions for the remote station, not operator source files.
  • Remote workflow: a caller usually sends <BLR> to refresh the root view, reads the helper entry for the location, types the alias such as INTEL or HUBS BLUEBELL depending on the location policy, and then refreshes again. After that refresh, the live BBS view contains the actual files from that location. ROOT, BACK, EXIT, or LOCK returns them to the main menu.
  • Protected-location helper: if a caller types an alias that requires a code but does not include the code, CommsPlan can publish a helper message for that alias instead of leaving the caller stuck in the current view. The intent is friendly: tell them what went wrong and how to try again, for example Incorrect Code provided for HUBS - try again or return to ROOT.
  • Location view behavior: only one vault view is published into the live BBS at a time. When a location is open, the remote station sees that location's files plus a helper entry telling them to type ROOT to return. The files are copied into the live BBS for pull; the source location remains in the managed vault.
  • Callsign-aware menus: root menu helper files should only be shown for aliases the caller is allowed to see. If a location is callsign-limited, stations outside that policy should not get a menu entry that invites them into a location they cannot use.
  • List in root menu: the clearest normal administration model is to list locations in the root menu and let access policy decide who sees them. Hide a location only when you deliberately want direct-access behavior with no menu advertisement.
  • FLAMP relay workflow: remote stations can ask for queue listings, available blocks, and individual block payloads without you manually swapping files in and out of the live BBS folder. The root menu can show BBS MSG - type FLAMP to see FLAMP BLOCK FILL CMDS - then refresh BBS.txt. After the caller types FLAMP, CommsPlan publishes separate helper files such as LIST Q, LIST F277, BLKS 0,8,9 F277, and ROOT. CommsPlan is forgiving about the request word: BLK, BLKS, BLOCK, and BLOCKS all mean "make a block file" when block numbers are included. To look before requesting, use LIST F277; BLKS F277 is treated as an incomplete block request and CommsPlan will publish a helper notice instead of guessing.
  • Adding received FLAMP files to relay: if a complete FLAMP file arrives through VarAC, open Messages. CommsPlan shows +Relay only when it can confidently identify the four-character queue ID from the filename or the FLAMP file content. That protects the relay list from guessed names. If +Relay is not shown, the file may still be readable, but CommsPlan is telling you it cannot safely add it to the relay queue automatically.
  • Library runtime status: Configuration, Ops Center, and the Messages BBS summary surface the last library action so operators can tell whether the library is enabled, active, reset, or degraded without opening logs.
  • Recommended setup order: start with normal BBS folders and verify BBS copy/archive behavior first. Then initialize the Managed BBS Library, confirm the imported default location, and add protected alternate locations only after the default is correct.
  • Credit: advanced VarAC BBS management in CommsPlan is being shaped with explicit credit to KG5RKW for the operational ideas behind Vault and BBS Access Guard.
  • BBS Access Guard concept: BBS Access Guard is not the same feature as Managed BBS Library. The library decides what CommsPlan publishes into live BBS folders. BBS Access Guard watches inbound VarAC file transfers and can log, delete, or quarantine files from unauthorized senders before they quietly blend into operator workflows.
  • Enable BBS Access Guard: turns on inbound file protection for received VarAC files.
  • BBS Access Guard mode: choose Log only, Delete unauthorized files, or Quarantine unauthorized files.
  • BBS Access Guard trust sources: choose whether files are allowed from Live BBS allowed callsigns, from callsigns marked TRUSTED in Operator History, or both. This is sender trust, not GPG/message-auth signature trust.
  • Sender validation: BBS Access Guard uses VarAC traffic-log/session evidence before applying trust. Portable forms such as W1ABC/P can match the base callsign W1ABC. If VarAC log evidence conflicts or the sender cannot be resolved, BBS Access Guard treats that as a protection event and records the reason.
  • Quarantine Dir: destination used when quarantine mode is selected. The field defaults toward Managed Root/quarantine.
  • Retry: how long BBS Access Guard waits between checks when VarAC has logged a receive event but the file is not fully visible yet.

Message Auth (Key/Hash) Details

Concept of use: Message authentication answers two different questions. First, “Did this file come from the signer I expected?” Second, “Did the contents change after that file was created?” CommsPlan supports both signature-based verification and hash-based verification because different operators and software workflows use different trust methods.

  • Signature vs checksum: a signature tries to prove both integrity and signer identity, as long as you trust the signing key. A checksum or hash proves only that the bytes match the expected digest; by itself it does not identify who created the file.
  • What a sidecar is: a sidecar is a separate helper file that travels next to the main file. For example, a message file may be accompanied by a separate signature file or checksum file instead of embedding that information inside the main payload.
  • Common sidecar patterns: in CommsPlan, a signed or verified FLAmp, VarAC, or BBS message file might appear as the main payload plus a companion such as .sig, .sig.k2s, .sig.b2s, .k2s.sig, or .b2s.sig. The naming is not always consistent in the field, so CommsPlan tries to verify the content relationship rather than trusting only one naming style.
  • Operational significance: if a file will drive action, planning, or reporting, operators should know whether they are trusting authorship, file integrity, or both. A successfully opened file is not the same as a verified file.
  • Trust model: verification is only as good as the trust decisions behind it. If a key is not trusted, a technically valid signature may still be operationally untrusted. Likewise, a matching checksum is useful only if you trust the source of the checksum.
  • Recommended practice: use signatures when possible for operator-to-operator trust, and use hashes as an additional integrity check or fallback when a signature workflow is unavailable.
  • Signature verification: Verify signed .k2s/.b2s message files and signature sidecars tells CommsPlan to look for supported signature patterns around FLAmp, VarAC, and BBS payloads and verify them against the available trusted keys.
  • Checksum verification: Verify .k2s/.b2s checksum sidecars tells CommsPlan to compare a payload against a separate digest sidecar when one exists. This is about file integrity, not signer identity.
  • Trusted hash actions: Add, Import Hash File, and Remove Selected manage hashes you want CommsPlan to treat as known-good reference values.
  • GPG executable path: this tells CommsPlan which local GPG program to use for key and signature checks. On some systems this may be gpg; on others it may be a full path selected with Browse.
  • GPG actions: Browse, Test, Refresh Keys, Import Key File, Import Armored Key, and Local-Sign Selected manage the local trust environment used for signature verification.
  • What an armored key is: an armored key is a text-form public key block, usually starting with -----BEGIN PGP PUBLIC KEY BLOCK-----. It is easier to share in email or plain text than a binary key file.
  • What local-sign means: locally signing a key does not change the original sender's file. It records that your local trust store considers that public key verified enough for your own operational use.
  • Key table columns: Trusted shows whether the key is currently trusted for your station, Fingerprint is the unique long-form identifier you should compare carefully, and User IDs are the human-readable identities attached to that key.
  • Trusted hash table columns: Use enables or disables that reference hash, Algorithm identifies the digest type, Hash is the expected digest value, and Label is your human-readable reminder of what that hash represents.
  • Default FLAmp signing key: chooses which local private key CommsPlan should use when signing outbound FLAmp traffic. Leave auto-select on if you only have one private key and do not need to choose manually.
  • Signing key passphrase: lets CommsPlan check or save the passphrase in the operating system credential store. It is not saved directly in the normal CommsPlan settings file.
  • Operational caution: do not treat a matching name or callsign in a key's user ID as sufficient proof by itself. The fingerprint is the safer identity anchor.

Condition Alerts

Purpose: define short received-message triggers that can ask the operator to change an SOP condition layer, with optional automatic application only for explicitly trusted rules.

  • Disabled by default: a rule does nothing until Use is enabled and its required group, level, pattern, and any sender/source/target/authentication constraints you deliberately chose are valid. Source and target may remain unrestricted, and Auth: none is valid when that is the reviewed policy.
  • Action choices: Suggest only records and surfaces the suggestion without applying it. Prompt to apply asks the operator. Apply automatically also requires the station-wide Allow trusted condition alerts to apply matching SOP layers automatically switch.
  • Trust and scope: review Group, Sources, Targets, Sender/Senders, Auth, Match, Pattern, SOP, and Action in the selected-rule details. A matching phrase from an untrusted or out-of-scope source must not change station posture.
  • RF Guard remains active: applying an SOP layer can change schedule intent, but it does not bypass RF Guard, radio authority, PTT interlocks, or final scheduler checks.
  • Rule actions: Add Rule creates a draft, Save Rules persists reviewed changes, and Delete Selected removes chosen rules. Reset MagNet Template restores the built-in MagNet MAGCON template as disabled while preserving custom rules.
  • Operational habit: keep match patterns short and unambiguous, limit accepted senders, require authentication where available, and test as a prompt-only rule before enabling automatic application.

SOP Export Details

Concept of use: SOP Export text lets you add station-specific context to the PDF version of your SOP without editing the generated tables themselves. Use it for a short introduction, local handling notes, distribution reminders, or closing instructions that should travel with the exported SOP.

  • Preamble: appears before the SOP export tables. This is a good place to explain the purpose, scope, effective time, or operator context for the document.
  • Postamble: appears after the SOP export tables. This is useful for closing reminders, document-control notes, or local operating cautions.
  • Placeholders: simple placeholders such as {{operator_callsign}}, {{as_of_local}}, {{as_of_utc}}, {{scope}}, and {{timezone}} are replaced during export.
  • Best practice: keep this text short and operational. The SOP tables carry the structured information; the preamble and postamble should explain how the operator should use or share the export.

Custom Tools Details

Concept of use: Custom Tools let you teach CommsPlan about helper programs that are specific to your station workflow but are not one of the built-in supported radio applications. Most often these are Python scripts, shell scripts, wrappers, emulators, or small utility launchers you want available from the same operational surface as the rest of the station tools.

  • Name: the operator-facing label CommsPlan shows in Configuration and Launch Control. Use a short, recognizable name that tells you what the tool is for.
  • Launch Command: the exact command CommsPlan should run. This can be a script path, an executable, or a full command line with arguments if your workflow requires it. If you can start it from Terminal with that command, CommsPlan should be able to use the same command.
  • What this is for: use Custom Tools for station-specific helpers that you want to launch intentionally from CommsPlan, such as emulators, monitoring helpers, conversion scripts, or other repeat-use operational utilities.
  • What this is not for: do not use Custom Tools to replace the built-in FLRig, FLDigi, JS8Call, VarAC, or other first-class integrations unless you deliberately need a custom wrapper. Built-in integrations carry their own readiness checks and cross-tab behavior that generic tools do not.
  • Ordering: Up and Down control the order Custom Tools appear when surfaced in Launch Control.
  • Add / Edit / Remove: these manage the saved Custom Tool definitions only. They do not automatically start the tool.
  • Cross-tab interaction: configured Custom Tools also appear in Launch Control, so the same named helper can be launched alongside your station software instead of living only as an external script on disk.
  • Best practice: if a command depends on a specific working directory, interpreter, virtual environment, or shell wrapper, include that intentionally in the command so the tool behaves the same way every time CommsPlan launches it.
  • Operational caution: CommsPlan can launch a Custom Tool, but it does not automatically understand that tool's internal readiness or state unless you build a separate integration for it. Treat Custom Tools as assisted launch helpers, not as full protocol integrations.

Launch Control Details

Launch Control is scoped to the radio selected in Configuration. Start controls appear first, followed by the application table. Launch details reveals configuration and monitoring guidance. Monitoring, automatic startup, and manual start are separate choices; changing one does not silently change either of the others.

  • Launch checked startup apps when CommsPlan opens: this radio-level switch controls unattended startup only. CommsPlan starts the checked rows when it opens only if this switch is on and the radio is also set to Use Radio. It does not disable the manual Start controls.
  • Monitor Health: includes that application in CommsPlan's health reporting for the selected radio. Turning monitoring off does not stop the application and does not change its startup selection.
  • Launch at Startup: adds that application to this radio's ordered startup set. Automatic launch requires the radio-level switch above. The explicit Start Startup Apps action runs the checked set now even when automatic launch is off.
  • Start: starts only that row's configured application instance now. It does not select the row for future startup and it does not change health monitoring. You may explicitly start a saved inactive radio's applications to prepare them; this does not activate that radio or make it command focus.
  • Order management: open Launch order for Up, Down, and Reset Default Order to control startup sequencing. This matters when one tool depends on another, such as JS8Spotter or CommStat needing JS8Call to be ready first.
  • Start Startup Apps: explicitly starts this selected radio's checked Launch at Startup applications in the displayed order without changing the automatic-start switch.
  • Stop Launch Sequence: stops an in-progress launch sequence. It does not necessarily close programs that already started successfully.
  • Multiple radios: each radio saves its own startup set, monitor choices, order, and automatic-start switch. Shared process identities are launched once; distinct radio-specific identities, profiles, paths, ports, arguments, and working directories remain separate. CommsPlan identifies a selected instance by its executable and exact profile/config/rig-name launch arguments, so an FT-DX10 process does not make the FT-710 row appear running or prevent the FT-710 instance from starting. Connected requires a fresh valid frequency read from the intended radio; an open endpoint or running process alone is insufficient.
  • Upgraded default JS8Call profile: an upgraded single-radio station keeps the installed JS8Call package's established default settings. If an older CommsPlan-generated JS8Call profile is still running after an update, CommsPlan will not terminate it or start a competing copy. Close that JS8Call window/process, then choose Launch again.
  • Configuration review warnings: if CommsPlan finds that an older canonical identity, manifest, or Software Administration projection no longer matches the saved launch projection, Launch Control reports the affected family as needing review but continues with independently valid reviewed recipes. CommsPlan still blocks malformed commands, resource collisions, unsafe native-configuration recovery, dependency failures, and receive-only authority violations.
  • Custom Tool crossover: Custom Tools configured in Configuration > Main > Custom Tools also appear here, which lets you keep station-specific helpers near the same launch workflow as your built-in software stack.

Logging and Diagnostics Details

  • Logging Level: controls how much detail CommsPlan writes to the log. Keep this disabled or low during normal use. INFO and DEBUG are best used only while troubleshooting because they can write more data and slightly reduce performance.
  • Enable DEBUG For: temporarily raises logging detail for troubleshooting and then automatically returns to the previous logging level. This is safer than leaving DEBUG on indefinitely.
  • Open Logs: opens the current log view so you can inspect recent activity.
  • Open Log Folder: opens the folder where CommsPlan stores log files.
  • Export Diagnostics: packages logs and troubleshooting context for support review. Use this when a support helper needs more than a screenshot.

Troubleshooting

  • If a button appears disabled, confirm required row selection or required fields.
  • If schedule behavior is unexpected, check Schedule Status first (paused/off-schedule/manual mode reasons).
  • If a Configuration section stays highlighted, open that section and look for a missing companion field such as DIRECTED.TXT, an endpoint port, an explicit native message source, or Incoming Files. A custom forms folder is optional; CommsPlan uses the station CP Forms Library, a clearly identified legacy fallback, or bundled forms when no station library is selected.
  • If FLDigi offset returns unexpectedly, open Configuration > Radios, choose the affected radio, and check Schedule Control for its FLDigi enforcement mode (On Schedule Change vs Prompt). Then confirm whether a new schedule row transition occurred.
  • If message actions are missing (for example +BBS), verify required Configuration paths are configured.
  • If VarAC does not launch from Launch Control on Linux, first clear VarAC Launch Command and test auto-launch from VarAC Install Folder. If needed, then set a custom Wine command using absolute paths.
  • If JS8Spotter/CommStat launch too early, keep JS8Call earlier in Launch Control order; CommsPlan now waits for JS8 API readiness before proceeding.
  • If BBS auto-archive does not run, turn on Enable Auto-Archive, confirm both BBS paths are valid and different, then open Messages once after startup.
  • If signature/hash states are neutral, verify Message Auth settings and trusted key/hash entries.
  • If Messages appears stale after its normal background catch-up, use the read-only preview under More... > Message Maintenance... > Message Index before deciding whether a rebuild is warranted.
  • For a recurring CPU or UI-stall report, preserve freqinout.log, the bounded rotated perf_metrics.log files, and any generated ui_hang_dumps. The hang snapshot contains bounded scheduler/projection state and redacts credential fields.
